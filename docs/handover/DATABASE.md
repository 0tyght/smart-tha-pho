# ฐานข้อมูลและการส่งมอบข้อมูล

[กลับคู่มือหลัก](README.md)

## 1. สิ่งที่อยู่ใน Git กับสิ่งที่ต้องส่งแยก

| รายการ | สถานะและความหมาย |
| --- | --- |
| SQL ใน `database/` | มีใน GitHub ล่าสุด 37 ไฟล์ ตรงกับไฟล์ในเครื่องที่ตรวจ |
| `bootstrap/` | 3 ไฟล์ สำหรับฐานข้อมูล ตารางตั้งต้น และ seed ข้อมูลอ้างอิง |
| `migrations/` | 30 ไฟล์ ตั้งแต่ 002–030 รวมเลข 027 สองไฟล์ เปลี่ยนทั้งโครงสร้างและข้อมูลบางส่วน |
| `demo/` | 4 ไฟล์ ข้อมูลสาธิต ไม่ใช่ข้อมูลใช้งานจริงทั้งหมด |
| ข้อมูลจริงใน MySQL/MariaDB | ไม่ได้ยืนยันสำรอง/export หรือเทียบ schema ที่ติดตั้งจริงในรอบนี้ |
| `storage/uploads/` | ไฟล์แนบส่วนตัว ถูก ignore ต้องสำรองแยก |
| `.env` และคีย์เข้ารหัส | ไม่อยู่ใน Git ต้องส่งทางปลอดภัย |

การมี SQL ใน Git ไม่ได้หมายความว่าข้อมูลล่าสุดในฐานข้อมูลจริงอยู่บน Git ด้วย ผู้รับมอบต้องได้รับ backup ฐานข้อมูลและไฟล์แนบที่สอดคล้องกัน พร้อมคีย์จำเป็น โดยไม่มีข้อมูลประชาชนหรือค่าลับใน repository สาธารณะ

## 2. การเชื่อมต่อ

`apps/api/src/core/config.js` อ่าน `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`; ค่าเริ่มต้นคือ `prms_tsm` บน `127.0.0.1:3306` ส่วน `core/db.js` ประกอบ `infrastructure/database/MariaDbConnection.js` ซึ่งใช้ `mysql2`

SQL หลายไฟล์ระบุ `USE prms_tsm` โดยตรง การเปลี่ยน `.env` เป็นชื่อฐานข้อมูลอื่นไม่ได้เปลี่ยนปลายทางใน SQL ต้องตรวจและจัด SQL สำหรับ environment ใหม่ก่อนนำเข้า ห้ามทดลองกับฐานข้อมูลจริง

## 3. เตรียมฐานข้อมูลใหม่สำหรับพัฒนา

1. ใช้ฐานข้อมูลแยกจากระบบใช้งาน สำรองก่อนหากมีข้อมูลอยู่แล้ว
2. อ่าน `database/bootstrap/create_database.sql` และ `create_tables.sql` ก่อนสร้างฐานข้อมูล/ตาราง
3. ถ้าต้องใช้ข้อมูลอ้างอิงตั้งต้น อ่าน `seed_data.sql` ก่อน migrations โดยเฉพาะ migration 010 ที่ปรับชื่อหมู่บ้าน seed นี้ไม่มีบัญชีผู้ดูแลที่พร้อมใช้จริง
4. อ่านและนำเข้า migrations ตามลำดับชื่อไฟล์ครบ 30 ไฟล์ ทั้ง `027_waste_incident_replacement_driver.sql` และ `027_waste_stop_collected_notice.sql`
5. สร้างผู้ดูแลตาม script ของโครงการ แล้วตรวจ schema, indexes, constraints, triggers และข้อมูลอ้างอิง
6. เลือกนำเข้า demo เฉพาะ environment สาธิตที่อนุญาต ไม่ใส่ demo ในระบบจริงโดยอัตโนมัติ

ขั้นตอนนี้ยังไม่ได้ทดสอบ fresh install หรือ restore ในรอบจัดทำเอกสาร ไม่ควรถือว่าสร้างฐานข้อมูลใหม่สำเร็จจนผู้รับมอบทดสอบจริงและบันทึกผล

## 4. ฐานข้อมูลที่มีอยู่แล้ว

ต้องสำรองและตรวจว่าแต่ละ migration ติดตั้งไปแล้วหรือยัง ไม่รัน bootstrap/seed/demo ทับ และไม่สรุปว่า migrations ทุกไฟล์เรียกซ้ำได้โดยไม่มีผลต่อข้อมูล

- `scripts/server/start-public.ps1` ปัจจุบันวนเรียก SQL ทุกไฟล์ตามชื่อ ไม่มีการข้ามไฟล์โดยอาศัยตารางบันทึกเวอร์ชันใน function `Invoke-DatabaseMigrations`
- migration 030 เปลี่ยน LINE เป็น `SMART` และลบแถว `CITIZEN/DRIVER` จึงต้องตรวจและสำรองค่าตั้งก่อนรัน ไม่มองว่าเป็นการเพิ่มคอลัมน์อย่างเดียว
- migration 027/028 มีส่วนเกี่ยวกับ trigger และ notification ต้องตรวจผลข้างเคียงกับคิวเดิม
- เลข migration ไม่ต่อเนื่องจาก 001 และเลข 027 ซ้ำเป็นข้อเท็จจริงของชุดนี้ ไม่ควรเปลี่ยนชื่อย้อนหลังโดยไม่ปรับกระบวนการและหลักฐานส่งมอบ

สำหรับงานต่อควรเพิ่ม migration runner และประวัติ schema version พร้อม checksum ที่ทดสอบแล้ว เป็นงานปรับปรุงภายหลัง ไม่ใช่เครื่องมือที่มีพร้อมในชุดปัจจุบัน

## 5. ตารางตามระบบ

| กลุ่ม | ตาราง/ชุด SQL ที่ควรเริ่มอ่าน |
| --- | --- |
| ร่วม | `users`, `villages`, `audit_logs`, `attachments`, `idempotency_keys` และ `system_line_channels` |
| สุนัขและแมว | `households`, `owners`, `pets`, `registrations`, `citizen_submissions`, `vaccination_records`, `sterilization_records`, ประวัติสัตว์/เจ้าของ และ LINE state/notifications |
| ขยะ | migration 015 เป็นต้นไป: ทรัพยากร ผู้ใช้บริการ เส้นทาง จุดเก็บ แผน ตำแหน่ง ผลเก็บ เหตุ และค่าบริการ |
| สาธารณภัย | ยังไม่พบ schema เหตุสาธารณภัยครบตามแบบออกแบบ |
| ประปา | telemetry ในเว็บเป็นข้อมูลจำลอง ยังไม่พบ schema ตามแบบเป้าหมายครบ |

ตาราง `cases` ที่มีใน bootstrap เป็นงานของทะเบียนสุนัขและแมว ไม่ใช่หลักฐานว่ามีระบบเหตุสาธารณภัยแล้ว แผนภาพ ERD ที่ออกแบบเพิ่มเป็นแบบเป้าหมาย ต้องทำ migrations และทดสอบก่อนใช้จริง

## 6. รายการสำรองและตรวจรับ

ผู้ดูแลส่ง backup ผ่านพื้นที่จำกัดสิทธิ์ ไม่ผ่าน Git สาธารณะ backup ต้องครอบคลุมข้อมูล โครงสร้าง triggers/routines ที่ระบบใช้และไฟล์แนบ ตรวจวิธี backup ตาม engine/version จริง และอย่าระบุ transaction-consistent หากมีตารางหรือกระบวนการที่ไม่รองรับ

- บันทึกวันเวลา timezone engine/version ชื่อ DB commit ของแอป และรายการ migration ที่ติดตั้ง
- เก็บ backup ของไฟล์แนบในช่วงเวลาที่สอดคล้องกับฐานข้อมูล พร้อมสิทธิ์เข้าถึง
- ส่งคีย์เข้ารหัสเดิมอย่างปลอดภัยสำหรับ LINE/MFA และข้อมูลเข้ารหัสอื่นที่ระบบใช้
- คำนวณ checksum และบันทึกผลตรวจไฟล์ ไม่เปิดเผย password/token ในคำสั่งหรือ log
- ผู้รับมอบ restore ใน environment แยก ตรวจความสัมพันธ์ จำนวนข้อมูลสำคัญ และการอ่านไฟล์แนบผ่าน API
- ป้องกันระบบที่ restore ส่งข้อความ LINE ไปผู้รับจริง: ใช้บัญชีทดสอบ/ค่าตั้งที่แยก และไม่เริ่ม scheduler ด้วย credential จริงโดยไม่อนุญาต
- ทดสอบ permission, Thai encoding, health/readiness, transaction และ workflow ตามระบบ
- แยกผล “restore สำเร็จ” จากผล “ทดสอบฟังก์ชันสำเร็จ” และบันทึกผู้ตรวจรับ

คู่มือนี้ไม่มี database dump หรือข้อมูลประชาชน และไม่ได้รัน migrations/backup/restore กับฐานข้อมูลจริง
